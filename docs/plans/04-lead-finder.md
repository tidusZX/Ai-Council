# Plan 04 — Lead Finder

## Context

[Migration 003](../../supabase/migrations/003_leads_crm.sql) (`clients`, `leads`, `outreach_logs`) is already applied. No service or UI exists yet. This plan ships **the smallest end-to-end loop**: a logged-in user can add a Singapore business, the system diagnoses its visual brand using existing Fly infrastructure, scores the opportunity, and surfaces a personalized outreach draft to copy/paste.

## North-star target

**5 retainer clients at $2k/mo = $10k MRR.** Targeting profile:

- **Mid-sized Singapore F&B**: multi-outlet restaurants, growing café groups, food brands with retail presence. NOT single-location cafés (too small to sustain $2k/mo).
- **Product brands** with active e-commerce + IG presence, ~10–100 staff, visibly weak photography.
- Probably need ~80 lead candidates in the funnel to land 5 retainers (6% close rate is realistic for cold outbound on a $2k/mo service).

This sharpens what the diagnosis step is grading: not "are these photos pretty" but "would replacing these photos plausibly drive enough business that $2k/mo is a no-brainer for them?"

**Guiding rule: reuse before we build.** Every new line of code should be justified against "can we reuse something already in this monorepo?" Below is the explicit reuse map.

## What's actually new (kept tight)

1. One new dashboard route group: `/leads` (list) + `/leads/[id]` (detail)
2. One new Vercel API route: `/api/leads/*` (CRUD + diagnose trigger)
3. One new endpoint on `analysis-service`: `POST /diagnose-lead` — accepts a list of image URLs + a business name, returns a structured diagnosis
4. One new database-types regen after `npm run db:types`
5. A handful of React components (LeadCard, DiagnosisPanel, OutreachDraft) — styled after existing `CouncilMemberCard`

---

## Goals (MVP — Plan 04A)

1. User manually adds a lead in `/leads/new` (business name, IG handle, website — at least one of IG or website required)
2. System fetches 6–12 images from the lead's IG profile or website
3. `analysis-service`'s new `/diagnose-lead` endpoint scores the images on: brand consistency, image quality, styling/composition, photography opportunity score (0–100)
4. Diagnosis lands in `leads.diagnosis` jsonb, score in `leads.opportunity_score`
5. `/leads/[id]` shows the lead, the diagnosis, and a personalized outreach draft (DM-flavored) generated by the existing `Marketing Lead` council persona with a different system prompt
6. Sort the leads list by `opportunity_score desc` so the highest-value targets surface first
7. Lead status updates manually (new → qualified → contacted) via dropdown — no automation in 04A

## Non-goals (deferred)

- **Auto-discovery** (find leads via Google Maps Places, IG hashtag scraping) — deferred to **Plan 04B**
- **Outreach automation** (sending DMs, email integration) — deferred to **Plan 04C** (likely never; manual copy/paste is sufficient)
- **Bulk diagnose** — one lead at a time for MVP
- **IG cookies for protected profiles** — only use public IG profiles, or accept that some leads will fail (same constraint as Analyzer's Instagram limitation)
- **Embeddings / clustering of leads** — that's its own future plan, depends on Plan 05 (embeddings-service)
- **Mobile responsive** — desktop only

```
                              │

                       Supabase
                       leads.diagnosis jsonb
                       leads.opportunity_score
```

For lead image fetching, **prefer scraping website `<img>` tags over IG**:
- No cookies needed
- Photographers' sites usually have hero galleries
- If website missing or empty, fall back to public IG via yt-dlp (same tool already on Fly)

## Implementation phases

### Phase 1 — Schema + types
- Confirm migration 003 is applied (it is); regenerate types with `pnpm db:types`
- Add a TypeScript `LeadDiagnosis` shape to `database-types` extending the jsonb

### Phase 2 — Backend: `/diagnose-lead` on analysis-service
- New route in `services/analysis-service/src/index.ts`
- Reuse `claude-analyze.ts`'s prompt-building structure, swap the system prompt
- Input: `{ business_name, business_type, image_urls: string[] }`
- Output: `{ diagnosis: {...}, opportunity_score: number }`
- Auth: existing `ANALYSIS_API_KEY` middleware

### Phase 3 — Dashboard API: `/api/leads/*`
- Following the `/api/video-jobs` pattern exactly:
  - Supabase auth check → DB write/read → proxy to Fly with `INGESTION_API_KEY`/`ANALYSIS_API_KEY`
- One new env var on Vercel: `ANALYSIS_SERVICE_URL` (already exists for ingestion proxy, just adding analysis URL)

### Phase 4 — Dashboard UI: `/leads`
- `LeadList.tsx` — sortable table, styled after existing analysis card
- `LeadForm.tsx` — copy of `AnalyzeForm.tsx`, swap fields
- `LeadDetail.tsx` — diagnosis panel + outreach draft + status dropdown
- Add `/leads` to the sidebar nav

### Phase 5 — Outreach drafting
- Extend `council-config` with a new persona: `outreach_writer` (system prompt focused on personalized DM/email writing in Shaq's voice)
- Call from `/api/leads/[id]/draft-outreach` — takes the diagnosis, returns 1–2 outreach options
- Surface in UI with a "Copy" button per draft, "Mark as sent" CTA that writes an `outreach_logs` row

### Phase 6 — Verification
- Manually seed 3 real Singapore F&B businesses with known IG/website
- Run end-to-end: add → diagnose → see diagnosis → see drafts → mark sent
- Confirm `opportunity_score` ordering is sensible

## Open questions

1. **What defines a Singapore F&B lead?** Is the input always a business with a website? Always an IG handle? Both?
2. **What does "diagnosis" actually grade?** Need 4–6 specific dimensions, decided before Phase 2. Suggest: brand consistency, photo quality, lighting, styling/composition, current visual hierarchy, opportunity-for-Shaq-specifically.
3. **Outreach voice** — should it match Shaq's existing voice in emails/DMs? If so, we'd want a few examples to fine-tune the persona prompt.
4. **Do we want to manually mark a lead as "already a client"** (and skip diagnosis), or do `clients` and `leads` live entirely separately?

## What this plan explicitly does NOT do

- Does not add a new service. Reuses `analysis-service` with a new endpoint.
- Does not add a new package. Extends `council-config`.
- Does not require Plan 05 (embeddings) to ship.
- Does not require any new third-party integrations beyond what's already in `analysis-service`.
- Does not commit to channel automation. Manual copy/paste is the v1 outreach UX.
